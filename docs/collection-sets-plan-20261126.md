# 收藏套組管理（Collection Set Management）｜規劃（2026-11-26，候選）

對應 CURRENT_TASK #32（2026-11-26 新增）。**緣起**：使用者以《詭鎮奇談卡牌版》為例，提出多層套組的需求：系列大套組 → 循環小套組 → 主擴充與神話包；獨立劇本直接歸屬大套組；一張採購可以橫跨多個循環；一個循環可以分多次買；同一個循環還有新舊兩種出版方式。使用者另外提供一份外部設計意見（方案 C：獨立的階層式收藏套組），並要求 Claude 參考該意見重新規劃，**但不採用其中第十二點「給 Codex 的指令」**。所以第一階段的唯讀核對由 Claude 直接完成，結果放在 §2。

狀態：Q104～Q106、Q108、Q109 **已採納**（DECISION_LOG SET-Q104～Q109，2026-11-26）；**Q107 未決**，改為另外討論共用配件（[備忘](shared-accessories-notes-20261126.md)，CURRENT_TASK #33）；S1 的資料模型要保留「同一款遊戲屬於多個套組」的可能。Q105 補充：成員與歸屬建立後可以修改。本文件只做靜態閱讀；沒有執行測試或 SQL，也沒有讀正式資料。後續階段**需要 Migration**。外部意見中的金額、完成度與介面圖都是模擬資料。

## 1. 採納外部意見的部分與修正

**採納的核心觀念**：商品結構、收藏（實體）、採購（交易）、套組歸屬是四個獨立的概念，不能互相綁定。套組只負責組織、歸類、完成度與統計；套組不清點，也不產生副本；成本一律引用既有的採購分攤，套組本身不存成本。

**和 repo 現況核對後的修正**：

1. 外部意見寫「維持原決策 Q98、Q103」。實際上 **#31 的 Q97～Q103 都還是候選，沒有採納**（DECISION_LOG 沒有這些條目）。所以不是「維持」，而是建議 #31 暫停，等本模組 S1 決策後再重新整理（§6）。
2. 外部意見把「成本去重依據」留給 Codex 核對。核對結果：系統裡**代表一筆成本的唯一身分是 `v2_purchase_allocations` 的一列**（Confirmed，§2 第 6 項）。只要以「分攤列」去重，同一個商品出現在多個套組也不會重複計算；同一商品有兩個副本時，兩筆分攤會各自計入。
3. 外部意見提到「實際成本與分攤成本要分開」。這個資訊**已經存在**：每一筆分攤都記錄了 `allocation_method`（`direct`、`manual`、`weighted` 等，Confirmed）。統計可以直接標示哪些金額是按比例估算的。
4. 外部意見的總額是單一數字。實際上**成本是依幣別分組的**（`series-spending.ts` 依 `currency_code` 分組），系統裡也沒有匯率；所以套組小計必須按幣別分開顯示，不能直接加總成一個數字。
5. 外部意見要求「未購入的商品也能是套組的預期項目」。現有收藏關係**只能連接已建立的收藏紀錄**（Confirmed），所以套組成員不能直接用收藏關係表示，必須能指向「遊戲身分」本身（§4）。

## 3. 方案比較（採用外部意見的 A／B／C）

| 比較項目 | A：bundle 收藏 | B：分組欄位 | C：獨立的階層式套組 |
| --- | --- | --- | --- |
| 多層 | 要放寬 `bundle_contains` 的規則 | 只有一層 | 支援 |
| 未購入的項目 | 不行（關係只能連收藏，見 §2 第 2 項） | 不行 | 可以（成員指向遊戲身分） |
| 成本重複計算 | 高（Q65 會另列禮包） | 低 | 用分攤列去重，可控制 |
| 對既有規則的影響 | 大（要改 `bundle_contains`，Q65 也受影響） | 小 | 小（新增獨立的表，不改既有語意） |
| 開發成本 | 中高 | 低 | 中高（要分階段） |

**建議：C**。理由和外部意見相同，再加上 §2 第 2 項：只有 C 能表達「還沒買的那幾盒」。

## 4. 候選資料模型（S1，供決策參考，尚未設計細節）

- **`v2_collection_sets`**：`id`、`parent_set_id`（可空，最上層為 NULL）、`name`、`sort_order`、`notes`、`revision`、`archived_at`。觸發器要擋下循環（父層不能是自己的後代），並限制最大深度。
- **`v2_collection_set_members`**：`set_id`、成員身分（**遊戲身分** `BGG:n`／`NotBGG:n`，和 #30 的資格規則一致）、`role`（必要或選購，S3 才會用到）、`sort_order`、`archived_at`。
  - 是否已收藏由查詢推導：該遊戲身分有沒有未封存、狀態為擁有的收藏。這個狀態**不存在成員表裡**。
  - 同一個遊戲可以出現在多個套組。
- 移除套組或成員**不會**動到收藏、副本、採購（只是標記封存）。
- 成本：套組小計 = 子樹內所有成員對應收藏的**分攤列，依 id 去重後**，按幣別加總；估算的金額另外標示。
