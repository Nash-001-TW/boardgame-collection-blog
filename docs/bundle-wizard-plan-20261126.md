## 1. 現況盤點（2026-11-26 靜態閱讀）

| 步驟 | 現有寫入 | 特性 |
| --- | --- | --- |
| BGG 同步 | `syncBggBatch`（`/api/admin/bgg`，`action: 'sync'`） | 一次最多 3 個 ID，每筆之間等 2 秒；有同步鎖與命令表冪等；會呼叫外部網路。**#30 起，同步成功的遊戲可以直接新增收藏** |
| 新增收藏 | `CollectionV2Writer.create`（`collection-v2-management.ts`） | 一筆收藏（可同時建一份副本、一張採購）在一個 `db.batch()` 內完成，用 `v2_collection_management` 做冪等；類型依遊戲自動決定（base／expansion／accessory），**不能建立 `bundle` 類型** |
| 收藏關係 | `writeRelation`（`relation-admin.ts`） | 一次一筆；類型有 `expansion_of`、`requires_base`、`accessory_for`、`bundle_contains` 等；有方向與類型檢查 |
| 採購 | `writePurchase`（`purchase-admin.ts`） | 一張訂單最多 30 行，每行可指定收藏；分攤方式有手動、直接、加權比例（`proportionalAllocation`）；明細類型包含 `bundle` |

**關鍵限制**：這三種寫入各自獨立。如果精靈只是在前端依序呼叫它們，中途失敗就會留下「收藏建了一半、關係沒建、採購沒記」的狀態。AGENTS.md 4-4 要求相關寫入必須原子提交。

## 2. 固定規則（不需決策）

1. 每一個品項仍然是一筆獨立的收藏，類型依 BGG 自動決定，和手動新增的完全相同，統計結果也一致。
2. 系統不新增「套組」資料表，也不改既有的資料結構。
3. 只能選擇同步成功的 BGG 遊戲或 NotBGG 遊戲，沿用 #30 的資格規則（§2-1）。
4. 套組總價以整數最小貨幣單位記錄，分攤後的總和必須等於總價，不能多也不能少（沿用 `proportionalAllocation`）。
5. Admin 新頁面的版面要先經過使用者確認（AGENTS.md 第 5 節；UI-D 系列「版面決策先看效果」）。

## 4. 非目標

- 從 BGG 自動找出某個套組包含哪些內容。BGG 的資料結構不一定有這個資訊，所以品項由使用者自己輸入 ID。
- 修改既有的新增收藏、關係、採購頁面行為（Q97 選 A 時，只是把 SQL 抽成共用函式，既有行為不變）。
- `bundle` 類型的收藏與 `bundle_contains`（Q98 選 A 時）。
- 收藏「需要清點」欄位（P0-D）。
- 編輯既有套組。精靈只負責新增；之後的修改，到各收藏與採購頁處理。
