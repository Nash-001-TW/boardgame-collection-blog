## 2. 架構：兩個業務領域、四種關聯來源

| 來源 | 存放 | 可否修改 | 現況 |
| --- | --- | --- | --- |
| BGG 原始關聯 | `bgg_games.cache_json` 即時計算 | 唯讀 | expansions／implementations／compilations |
| 手動遊戲關聯 | `v2_game_relations`（manual） | 新增、編輯、封存 | 1 筆 |
| NotBGG 配件關聯 | `site_game_relations` | 由 NotBGG 流程管理 | 0 筆，只有 accessory_for |
| 收藏組合 | `v2_collection_relations` | 新增、編輯、封存 | 3 筆 |

前三種屬於遊戲層，最後一種屬於收藏層。

**遊戲層有效關聯檢視（Effective Game Relations）**：不新增資料表，只新增一個共用的伺服器端讀取與判定模組（候選名稱 `src/lib/effective-game-relations.ts`），統一負責：

- 讀取遊戲層三種來源，並解析身份（BGG／NotBGG 別名）。
- 做等價判定與去重（§3）。
- 給以下功能共用：公開頁相關遊戲、收藏組合帶入建議、收藏組合的遊戲關聯狀態、遊戲關聯管理的來源篩選、跨層建立前的重複檢查、反向建立收藏組合。

避免每個功能各寫一套 BGG 與手動關聯的比對。BGG 快取不可用時，回傳「判定不可用」，不得當成「沒有關聯」（Q190）。

## 3. 等價判定與去重（Q184、Q186、Q187）

### 3.1 等價條件（全部成立才算同一筆）

1. 來源遊戲解析後為同一身份（含 BGG／NotBGG 別名）。
2. 目標遊戲解析後為同一身份。
3. 類型等價（見 3.2）。
4. 方向一致：依賴型類型必須同方向；不限方向類型是否可反向等價，依既有重複規則（`relation-admin.ts:5`）只限 standalone_related、same_series、integrates_with。
5. 兩筆都符合各自來源的有效條件（未封存；手動須已確認才可公開；BGG 快取須成功同步）。

### 3.2 BGG kind 與手動類型的對應（候選）

| BGG kind | 可視為等價的手動類型 | 條件 |
| --- | --- | --- |
| expansions | expansion_of | 方向已判定（role 不是 unconfirmed），且方向一致 |
| expansions | requires_base | **不等價**。BGG 無法區分「必要」與否 |
| compilations | compilation_of | 只在方向已確認時；目前方向判定一律 unconfirmed，等同不等價 |
| implementations | 無 | 不對應任何手動類型 |
| （無配件連結） | accessory_for | BGG 不可能「已有」配件關聯 |

- requires_base 與 expansion_of 不互相等價（循環檢查同族不代表語意相同）。
- 不同類型永遠不合併，例如 228→231 expansion_of 與 228→231 requires_base 是兩筆。

### 3.3 去重只影響呈現

| 情境 | 結果 |
| --- | --- |
| BGG 與手動同時存在且等價 | 合併成一筆顯示，保留兩個來源標記 |
| BGG 關聯消失 | 依手動關聯顯示 |
| 手動關聯封存 | 依 BGG 關聯顯示 |
| 兩者都不存在或無效 | 不顯示 |
| BGG 類型或方向變更 | 重新判定 |

不因去重而刪除、修改或封存任何原始資料（Q187）。手動關聯 #1 保留。

## 5. 跨層衍生狀態（Q177）

即時計算，不新增持久化欄位。拆成四個維度：

| 維度 | 值 |
| --- | --- |
| 對應狀態 | 已有、可補建、不可建立、不適用、判定不可用 |
| 來源集合 | BGG、手動、NotBGG、兩者以上、無 |
| 手動確認 | 已確認、未確認、不適用 |
| 原因（不可建立、判定不可用時） | 缺少對應遊戲、類型或方向不符、會形成循環、BGG 快取不可用、讀取失敗 |

判定順序：
1. 收藏組合是 bundle_contains → **不適用**。
2. 任一端收藏沒有有效遊戲 → **不可建立**（缺少對應遊戲）。
3. 讀取失敗或需要的 BGG 快取不可用 → **判定不可用**，不得顯示「可補建」。
4. 有效關聯檢視中有等價關聯 → **已有**（附來源集合與確認狀態）。
5. 預檢遊戲層方向、循環、別名守衛：通過 → **可補建**；失敗 → **不可建立**（附原因）。

「存在關聯差異」不另立狀態：同一對遊戲有其他類型的關聯時，只在「已有」或「可補建」旁加提示，不判定為衝突。

以現有資料為例：

| 收藏組合 | 對應狀態 | 來源 | 手動確認 |
| --- | --- | --- | --- |
| #263 → #262 | 已有 | BGG＋手動 | 已確認 |
| #264 → #262 | 可補建 | 無 | 不適用 |
| #265 → #262 | 可補建 | 無 | 不適用 |

## 6. 雙向建議（Q176、Q178）

### 6.1 收藏 → 遊戲（建立收藏組合時帶入）

選定來源收藏後，從有效關聯檢視找出以該遊戲為端點的關聯，再找出你擁有的另一端收藏：

| 優先 | 來源 | 行為 |
| --- | --- | --- |
| 1 | BGG 已判定方向的關聯 | 顯示「使用此建議」 |
| 2 | 已確認的手動關聯 | 同上 |
| 3 | 未確認的手動關聯 | 顯示，標示未確認 |
| — | 名稱相似、同系列推測 | 不納入 |

- 同一遊戲對應多筆收藏（不同版本、語言、紀錄）時，全部列出由使用者選，不自動選第一筆（Q178）。
- 只在同一 `record_scope` 內建議。
- 已有相同收藏組合時，顯示「已建立」，不重複建議。

### 6.2 遊戲 → 收藏（遊戲關聯頁反向建立）

| 收藏狀況 | 顯示 |
| --- | --- |
| 兩端都有收藏，且已有收藏組合 | 「查看組合」 |
| 兩端都有收藏，尚未建立組合 | 「建立收藏組合」（帶入表單） |
| 同一遊戲有多筆收藏 | 選擇來源與目標收藏 |
| 只有一端有收藏 | 提示缺少哪一端，不提供建立 |
| 兩端都沒有收藏 | 不顯示入口 |
| 類型屬 C 級 | 不提供映射 |
| 收藏層方向檢查不通過 | 顯示原因 |

不會因此新增不存在的收藏紀錄。

## 7. 跨層寫入與守衛（Q171、Q172、Q182）

### 7.1 新增伺服器動作（API 新增，需批准）

候選：`POST /api/admin/relations` 新增 `action: 'save-with-game'`（或獨立端點），一次送出收藏組合與遊戲關聯，放在同一個 `db.batch`：

1. 收藏組合條件寫入 → 操作紀錄 A（`result_id NOT NULL`）
2. 遊戲關聯條件寫入 → 操作紀錄 B

任一條件不成立，紀錄寫入失敗，整批回滾，兩層都不寫入。

### 7.2 守衛

| 風險 | 處理 | 現有 Schema 是否足夠 |
| --- | --- | --- |
| 兩個請求同時建立 | 重複檢查在同一條 SQL 的 WHERE 中，D1 依序執行 | 足夠 |
| 循環 | 觸發器在寫入時檢查 | 足夠 |
| 預覽後遊戲類型、BGG 快取變更 | 遊戲層既有快照守衛 | 足夠 |
| 預覽後收藏更換對應遊戲 | **新增**：收藏層守衛釘住 `c.game_id = 預覽時的遊戲 ID` | 足夠，只改 SQL |
| BGG 已有等價關聯 | **新增**：伺服器重新以有效關聯檢視判定，已有就不寫遊戲關聯，只建收藏組合，並在回應中說明 | 足夠 |
| 手動關聯已存在 | 沿用，不修改其確認狀態 | 足夠 |
| 連點兩次、回應遺失後重送 | 同一 `request_key` 回傳原結果；兩筆紀錄使用由主鍵衍生的兩個子鍵 | 足夠 |
| 只成功一層 | 同一 batch，不可能 | 足夠 |

結論：**不需要 Migration**。需要的是新增一個伺服器動作，以及收藏層守衛加上 game_id 快照；兩者都屬於 API 與寫入邏輯變更，需要批准。

### 7.3 驗證失敗（Q172）

- 預覽時就顯示遊戲層的檢查結果，不通過時「同時建立遊戲關聯」不能勾選，並說明原因。
- 送出時伺服器重新驗證；任一層失敗，整筆拒絕，回應註明是哪一層。
- 取消勾選時，只建立收藏組合（沿用既有 `save`）。

### 7.4 確認與公開（Q170）

- 遊戲關聯的「公開顯示（確認）」**預設不勾選**。收藏組合沒有確認狀態，不存在可傳遞的確認。
- 已存在的手動關聯，不因這次操作改變確認狀態。

## 9. 版面規劃

### 9.1 收藏組合管理（桌面）

- 頂部統計：收藏組合 3 · 已有 1 · 可補建 2；篩選：全部／已有／可補建／不可建立。
- 清單每列：來源收藏 → 類型 → 目標收藏；「遊戲關聯」欄顯示對應狀態，加上來源標籤（BGG、手動）與確認標籤；操作欄依狀態提供「查看」「補建」「查看原因」。
- 收藏組合本身**不顯示**「已確認」（沒有這個欄位）。

### 9.2 375px 手機

延續 #45 的緊湊卡片：第 1 行類型；第 2、3 行來源與目標收藏；第 4 行遊戲關聯狀態摘要（例如「BGG＋手動」「可補建」）加上右側操作按鈕。不另外加大型區塊。

### 9.3 新增收藏組合對話框

1. 來源收藏 → 顯示建議（§6.1），可點「使用此建議」。
2. 類型、目標收藏。
3. 預覽區：收藏組合（待建立）＋對應遊戲關聯（檢查結果：通過、BGG 已有、不可建立及原因、不適用）。
4. 勾選「同時建立遊戲關聯」（依 §4 預設）與「公開顯示（確認）」（預設不勾）。
5. 摘要：本次建立收藏組合 N 筆、遊戲關聯 N 筆。

### 9.4 遊戲關聯管理

- 新增來源篩選：全部關聯／BGG 原始／手動關聯（Q188）。BGG 列唯讀，標「BGG 原始」。
- 等價的 BGG 與手動關聯合併成一列，同時顯示兩個來源。
- 每列顯示「我的收藏」：依 §6.2 提供「查看組合」或「建立收藏組合」。
- BGG 快取可能指向本機沒有的遊戲；全部列出的查詢成本與分頁方式在 B 階段實作前評估，先限定為「至少一端是本機遊戲」。

UI 實作前照 AGENTS.md 先給使用者看截圖確認。
