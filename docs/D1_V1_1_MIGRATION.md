# D1 V1.1 安全遷移與回復計畫（只規劃，未執行）

> 重要：本文件不是執行授權。Codex **不得**自行執行 migration、遠端 SQL、資料修正、部署或刪除。先完成分析並取得明確授權。

## 1. 遷移原則
- **增量優先、原始資料保護、可分批、可核對、可重試**。
- 不覆蓋 `v2_games` 224、`v2_collection_items` 256、`v2_component_definitions` 178、`v2_sleeve_requirements` 786（2026-10-22 觀測值；正式執行前需重新查詢）。
- `v2_owned_copies`／訂單表當時為空，不代表可無條件 DROP；執行當天先重查。
- 舊收藏實體化必須有使用者逐項確認數量、版本、語言；未確認資料保持不變。
- migration 檔案依現有 `migrations/` 編號新增，**不修改已執行的歷史 migration**。
- 正式 D1 備份與可還原性測試是進入寫入階段的必要條件。

## 2. 階段 0 — 唯讀盤點與風險分析（Codex 可先做）
1. 讀取專案路由、資料存取層、migration、`wrangler.json`，列出所有讀寫 `v2_purchase_orders`、`v2_owned_copies`、卡套表的程式位置。
2. 比對 `docs/reference/d1_v2_schema.json` 與 migration 定義；盤點 21 張表的 PK、FK、CHECK、UNIQUE、索引、Trigger。
3. 確認當前遠端表筆數、scope、狀態分布及異常資料；**任何遠端查詢也需使用者同意，預設只做本機靜態分析**。
4. 明確記錄 schema 與程式不一致、SQLite/D1 相容性、舊欄位被哪些 UI/API 使用。
5. 提供差異報告及決策問題，不修改任何檔案。

**驗收：** 表與路由對照完整、風險列表有依據、無任何寫入／部署。

## 3. 階段 1 — 實作方案核准（不寫 DB）
- 定稿最小必要新增表、欄位、外鍵、索引、Trigger；特別釐清 receipt_units/provenance/acquisitions 單一權威。
- 定稿 `draft` 方案：保留舊 status + 生命週期表，或受控表重建；提供對現有程式的影響矩陣。
- 定稿 TWD minor unit、舊財務彙總欄位處理、正式快照與套組內容的凍結策略。
- 產生 SQL 草稿／測試案例（僅在使用者明確授權產檔後）；**不套用**。

**驗收：** 用戶批准 schema、風險、測試、回復方案後才進下一階段。

## 4. 階段 2 — 備份／測試環境
- 在取得授權後備份遠端 D1，記錄時間、資料庫識別、Schema 版本、資料筆數、備份校驗及復原步驟。
- 在隔離的本機或測試 D1 執行 migration，**不得直接以正式 DB 當測試庫**。
- 驗證外鍵完整性、唯一鍵、CHECK、Trigger、既有頁面查詢；使用專門測試資料。
- D1 的 batch／transaction 語意以目前使用的 Wrangler／Workers D1 API 官方文件與實測為準，不假設任意 SQL BEGIN/COMMIT 可直接使用。

**驗收：** migration 可重複部署到乾淨測試庫；失敗時不殘留半成品；復原演練成功。

## 5. 階段 3 — 增量 Schema 部署（僅授權後）
- 優先 CREATE 新表及新索引；避免修改既有資料列。
- 涉及現有 CHECK 的狀態變更，先測試受控重建或相容層；不得直接將 `draft` 寫入舊 status。
- 部署後核對：原表資料筆數與校驗摘要不變、外鍵檢查通過、原功能仍可正常運作。
- 每一 migration 有前置條件、版本紀錄、預期變更、失敗處理。

**驗收：** 舊資料不變、既有功能不退化、新 Schema 可供下一階段測試。

## 6. 階段 4 — 功能測試與正式流程
至少涵蓋：
- 草稿不產生正式編號，不入正式財務／收貨；正式化凍結 snapshot。
- 套組版本變動不影響已正式訂單；套組售價只計一次，內含商品不另計價。
- 分批到貨與同批多份、重複 request、斷線重試、超收、錯誤商品、跨訂單錯配。
- 同一 receipt_item 的 unit_index 唯一、同一 owned_copy 不重複綁定。
- 付款、部分付款、分期、退款、折扣、費用修正與重開結算；不能雙重計算舊彙總欄位。
- 缺件補件 vs 整盒換貨、退貨、補寄、作廢及稽核歷史。
- 卡套需求／庫存既有功能不回歸失敗。

**驗收：** 自動測試＋人工驗收紀錄，無重複收貨、無負庫存／超額退款、無資料孤兒。

## 7. 階段 5 — 舊收藏人工確認與實體化（獨立授權）
1. 讀取 254 筆 `production/owned`（執行前重查），產生待確認清單，不直接寫入實體。
2. 人工確認每項實際數量、版本、語言；同一項多版本分組，保留尚未確認資料。
3. 每批先產生預覽：待建立份數、每份識別、對應 collection_item、來源類型、警告與衝突。
4. 使用者批准批次後，原子寫入確認套用與 owned_copies；來源對照有唯一鍵，重試不重複建立。
5. 比對「確認份數 = 新建實體數」，保存對照與稽核；不更動 `v2_collection_items` 原紀錄。
6. 2 筆 `preordered` 不納入舊藏品實體化，須等正式收貨。

**驗收：** 每批確認可追溯、可重試、不猜測未確認資料、不覆蓋卡套需求。

## 8. 回復與錯誤處理
- **尚未寫入：** 取消方案即可，無 DB 回復需求。
- **新增空表／索引失敗：** 依 migration 紀錄與 FK 依賴評估；不得在正式庫任意 DROP。
- **正式交易已存在：** 以補償交易／作廢／稽核修正，不直接 DELETE 已完成訂單／收貨／退款。
- **整體故障：** 依經驗證的 D1 備份／復原方案，評估備份後新增交易的保全與停機窗口；復原前需人工授權。
- **雙寫過渡：** 必須指定單一權威來源與一致性檢查，不允許永久兩套真相。
