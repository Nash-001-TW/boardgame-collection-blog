# 收藏卡套頁改版規劃（#38）

- 日期：2026-11-27（Asia/Taipei）
- 狀態：Q137～Q142 **已採納**（使用者「全部採建議」，DECISION_LOG SLEEVE-UX-Q137～Q142）；**已授權實作**（2026-11-27，DECISION_LOG SLEEVE-UX-AUTH）。
- 起因：使用者在正式環境操作「小小史詩克蘇魯豪華版」（#262）的卡套頁時回報 5 個問題：卡片太大、同尺寸要重複建立、已建需求的組件仍在選單中、尺寸沒有排序、扣帳確認文字難懂，以及「尚未套用」的區塊太佔空間。另參考使用者提供的外部意見（第九點不採用）。

## 1. 現況（程式與正式資料唯讀核對）

- 畫面：`src/components/admin/SleeveWorkflowPanel.astro`；需求表單：`SleeveRequirementForm.astro`；資料：`src/lib/sleeve-workflow.ts` 的 `readSleeveWorkflow`；前端：`src/lib/sleeve-workflow-controller.ts`。
- 每筆需求都是一張大卡片：狀態、組件、說明、編輯，每個副本底下還直接攤開套用表單。
- 尺寸沒有卡套產品時，`canApply` 不檢查產品，仍會顯示套用表單，但產品下拉是空的，送不出去。
- 尺寸選項依 `v2_sleeve_sizes.id` 排序（`ORDER BY id`），也就是建立的先後順序。
- 組件下拉列出所有可指派的卡牌組件，不排除已經建過需求的組件。資料表沒有「一個組件只能有一筆需求」的限制，同一組件可以有多種尺寸的需求，這是合法的。外部意見提到的 S16，在 repo 裡查不到紀錄。
- 扣帳確認勾選框（`notPreviouslyRecorded`）在 API 端是必填（`sleeve-workflow.ts` 的 `SLEEVE_CONFIRMATION_REQUIRED`）。
- 正式資料：#190 書頁卡牌的預期數量是 30，副本 #1 清點也是 30，但需求 #787 寫 35 張，差異可以直接從結構化欄位比對出來。88 × 126 mm 目前有 5 筆需求，共 13 張；加上棄除墊 1 張就是 14 張。

## 3. 第一階段：畫面精簡化（只改 UI，不動 API 和 Schema）

1. **總覽列**：總需求、已套用、尚需套用（以張數計算，分副本顯示）。
2. **依尺寸分組**：每組的標題寫「45 × 68 mm · 1 種組件 · 共 35 張」。每筆需求一到兩行，例如「#787 · 書頁卡牌 · 35 張 · 副本 #1 0 / 35 未套用」，點一下才展開。
3. **篩選**：全部／未完成／已完成，記住上次的選擇（localStorage，失敗也不影響）。
4. **展開後依狀態顯示不同的操作**：
   - 沒有產品：「尚無此尺寸的卡套產品」，並附上連到卡套產品管理頁的連結，不顯示套用表單。
   - 未套用或部分套用：「套用卡套」按鈕，按下才出現表單。
   - 已完成：只顯示套用紀錄。
   - 已鎖定（已有套用紀錄）：照舊不能編輯。
5. **尺寸下拉**：依寬、再依高由小到大排序，相同尺寸再依 id 排序；可以輸入數字搜尋。最上面是「本收藏已使用的尺寸」群組。有產品的尺寸標示「（N 種產品）」。不會自動選擇相近的尺寸。
6. **勾選框文字**：照 Q141 修改。
7. **數量差異提示**：照 Q142。
8. 新增需求表單仍然收合在頁面上方。

## 4. 第二階段：建立需求更有效率

1. 組件下拉預設隱藏已經建過需求的組件，選項旁有「顯示全部」切換；顯示全部時，已建過的組件標註「（已有需求 #787，45 × 68）」。
2. **批次建立**：選尺寸 → 列出可指派的卡牌組件（預設隱藏已建過需求的組件）→ 勾選並填張數（預設帶入該組件在所選副本的清點數量，沒有清點數量就帶預期數量）→ 預覽「88 × 126 mm · 3 筆 · 共 14 張」→ 一次送出。
3. 批次 API：沿用既有的 Access、同源、限流、冪等與 revision 守衛；用 D1 batch 一次寫入；任何一筆不合法，整批都不寫入。單筆建立和編輯的既有 API 保持不變。
4. 建立完成後就地更新清單，不重新整理頁面，表單保留剛才選的尺寸。

## 5. 不在這次範圍

- 批次套用加扣帳（同尺寸、同產品、多筆需求一次扣帳）。
- 歷史套用補登（只記錄進度、不扣庫存）。
- 依清點數量自動修改需求張數。

## 6. 驗收重點

- 有十幾筆需求的收藏，在 1280 寬的畫面上，不必捲動就能看到所有尺寸分組的標題。
- 沒有產品的尺寸不會出現套用表單。
- 尺寸下拉依數值排序（例如 45 × 68 排在 88 × 126 前面），可以搜尋。
- 批次建立 3 個組件後，會有 3 筆獨立的需求；只要其中 1 筆不合法，就 0 筆寫入；重送同一個請求不會重複建立。
- 既有的套用扣帳流程（產品、張數、日期、勾選框、庫存扣除）行為不變；既有的卡套 Node 與 Edge 測試不回歸。
- 中英雙語；375 寬沒有水平捲軸。
- 介面要先給使用者看截圖，確認後才部署（AGENTS.md §5）。

## 8. 審查結果（2026-11-27，Claude）

- Codex 已實作第一、第二階段。新的 API 動作是 `POST /api/admin/sleeves`、`{"action":"requirements-batch","collectionId","copyId|null","sizeId","items":[{"componentId","quantity"}]}`：首次成功回 201 `{ids,replayed:false}`；用同一個 key、同樣內容重送回 200，`replayed:true`；同一個 key、不同內容回 409 `IDEMPOTENCY_CONFLICT`。寫入用一個帶守衛的 INSERT 加上收據；只要有任何一筆沒通過守衛，收據的 `result_id` 就會是 NULL，觸發 NOT NULL 限制，整批回滾。每筆仍有自己的 `source_key`（`key:位置`）。單筆的建立、編輯與套用扣帳 API 沒有變更。
