# D1-S1／S2 v2｜整合設計與技術候選

2026-11-19（台北）。使用者已正式採納 D1-17／D1-18，見 [Decision Ledger](Decision-Ledger-20261119.md)。D1-T01～T04 整合審查為附條件通過，技術選型與實作驗收仍待完成。本稿沿用 [第一版與證據保存方案 A](V2-D1-expected-quantity-correction-scope.md)，補充 [v1](V2-D1-correction-state-and-storage-review.md) 的缺口。

## 1. 已批准政策與寫入責任

| 決策 | 已批准規則 |
| --- | --- |
| D1-17 | 保留 R06 一般編輯與獨立的公告套用操作，兩者共用必要的版本守衛與變更歷史。共用預期量實際變更時，記原值、新值、理由、認證操作者與時間。公告勘誤另記公告版本、適用範圍及審查依據。 |
| D1-18 | 優先引用可信、不可變的歷史。能取得當時資料但缺乏穩定引用時，保存必要快照。已無法可靠還原的舊資料標 `UNKNOWN`，保留可證明的部分。 |

第一版共用預期量更正仍須確認全適用範圍，部分版本與版本不明時只保存證據及理由。普通編輯不能把部分版本勘誤當一般修正套用全收藏。既有 [R06 更新](../src/lib/physical-component-management.ts#L135) 會寫當前值並遞增 `physical_revision`，目前未保存前值歷史。實作設計須涵蓋所有預期量修改路徑。若只改名稱等欄位，或提交後預期量保持相同，不產生預期量變更歷史。

## 2. 逐目標狀態與證據失效

- 以不可變公告版本 × 共用組件定義為審查目標。網址可重用，公告修改需留舊版及新版本關聯。同一公告的不同目標獨立審查及提交。
- `PENDING` 可記待核或已確認但尚未提交；確認完全不適用或只涵蓋部分版本時記 `NOT_APPLICABLE` 及理由。證據或範圍改變時，可由管理員重開並保留舊理由。
- `APPLIED` 從已提交的成功更正推導，代表曾成功套用。後續更正不改寫舊紀錄。已套用目標不重開成待套用；新版勘誤另建目標。若確認所依公告已更新、審查已重開／改判或實際範圍依據已變，舊的未提交確認失效。證據及審查歷史仍可查閱。

## 3. 原子提交與重送

兩種操作的提交邊界共同核對授權、目標歸屬與資料範圍、未封存與分類資格、目前定義 revision 及預期舊值（含 `NULL`）。公告勘誤額外核對公告版本、審查判斷與實際用來確認全範圍的資料。若這些依據已改變，即使預期值仍是 103，也要重新確認。若採快照，還須保證快照引用或實點取自一致的狀態。副本版本欄位只供核對，不能自行證明公告適用。

候選優先沿用 D1 批次交易及 DB 中止守衛。一個成功提交同步寫預期量、更正歷史及可重播結果；條件式更新影響零列、歷史或回執寫入失敗時，整個更正應在交易邊界中止。不得等交易提交後才把零列改回錯誤。可比較由受守衛的更正寫入驅動更新的替代方案。具體 SQL 與機制未選。

| 結果 | 用戶端行為 |
| --- | --- |
| 已知成功 | 相同操作者、識別及內容回原持久結果，即使目前預期量後來已改變。 |
| 已知未提交 | 原值及審查狀態保留。仍有效的同一請求只能以原內容重試；確認已過期時重新核對後另起操作。 |
| 結果未知 | 以原識別核對或重送相同內容。沒有成功回執時保持未知，不換識別重做。 |
| 可確認仍在途 | 只在有可靠執行證據時回報；否則沿用結果未知。 |

不同識別同時操作同一目標，最多成功一筆。不同公告競爭同一共用定義，由舊值、revision 與範圍守衛拒絕過期操作。同一識別異內容必須拒絕，包括已知回滾後；舊識別不可過期後重新生效。識別簽發、期限、持久方式與清理，仍待技術選型。

## 4. 最小充分歷史證據

103 → 100 更正時保留實點 99、原清點日期、checked 與完成狀態。歷史要能區分「原清點當日」與「用更正當時仍有效的同一筆實點重算」。優先引用不可變的數量版本與清點事件，並保存判讀採用的規則版本。現有 [清點 upsert](../src/lib/physical-component-management.ts#L151) 會覆寫目前實點和系統時間，現值不足以補原歷史。

若當時可觀測到有效實點，但缺穩定引用，候選快照限於需要回溯的副本 × 組件，涵蓋副本／組件識別、實點及其來源或 revision、使用者清點日期或 `UNKNOWN`、更正前後預期量、採用的判讀規則、快照時間與關聯更正。快照可支持「當時用這個 99 判讀少 4／少 1」。缺少原始事件時，原清點當日的歷史仍標 `UNKNOWN`。附件保存期限、逐盒容量上限與儲存格式留待設計。

## 5. D1-10～D1-16 驗收增補

| 案例 | 應驗證 |
| --- | --- |
| D1-10 成功一致性 | 分開驗證 R06 手誤修正與公告勘誤。以勘誤 103 → 100 為例，實點仍為 99，revision、歷史及回執一致。核對兩種操作的歷史都有前後值、理由、操作者與時間；勘誤另含公告版本、適用範圍與審查依據。其他目標、原日期、checked 與完成保持原值；後續一般編輯不能改寫原回執。只改名稱或傳入相同預期量時，無預期量變更紀錄。 |
| D1-11 交易失敗 | 在兩條寫入路徑分別驗證零列更新、歷史寫入失敗及回執寫入失敗。原值、狀態與歷史均不留下半套用，也沒有新清點事件。 |
| D1-12 逾時與重送 | 覆蓋成功回應遺失、同識別異內容、已知回滾、可證明在途、結果未知與過期舊識別，回覆及副作用各自符合契約。 |
| D1-13 併發與範圍失效 | 同目標不同識別、不同公告同一定義、一般編輯撞勘誤、封存或範圍改變但舊值相同（含 `NULL`）。舊確認不得生效。另核對部分版本勘誤不能借一般編輯套用全收藏。 |
| D1-14 多目標 | A 套用成功，B 只涵蓋部分版本，C 交易失敗，各保留自身狀態及歷史。重播 A 不觸及 B 或 C。 |
| D1-15 公告更新與重開 | 同網址新版使舊未提交確認失效；重開保留舊理由；舊成功回執可在新版套用後重播。 |

## 7. 交給 ChatGPT 的審查摘要

D1-17 與 D1-18 已正式批准。R06 手誤修正與公告勘誤並存，所有實際共用預期量變更保留共用守衛、原值、新值、理由、操作者及時間。公告勘誤再保存版本、範圍與審查證據。既有兩項方案 A 仍適用：待核公告可先保存，只有涵蓋整個共用定義才可更正。歷史優先用不可變引用；缺引用但可取得當時資料時保存必要快照；無法回溯的部分標 `UNKNOWN`。

請先審查 §6 的 P0 候選，特別確認一般編輯與勘誤競爭時的共同守衛、零列更新能否在交易內中止、請求回執能否分清確定結果與未知，以及歷史快照能否與更正事實一致。以 §5 的 D1-10～D1-16 對照設計，P1 的公告及保留政策同步標出與 P0 的依賴。建議下一階段先授權唯讀技術選型與設計複審；任何原型、測試、SQL、Migration 或部署均需另行批准。狀態為 `EXECUTION_NOT_AUTHORIZED`。
