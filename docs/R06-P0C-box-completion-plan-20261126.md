## 1. 已採納規則摘要（不重新決策）

| 主題 | 規則 |
| --- | --- |
| N／M／U | **N**：已確認、且對此副本適用的組件種類數。**M**：其中已清點且實際數量有效（非負整數，0 有效、NULL 無效）的種類數。**U**：此收藏資格未確認的組件定義數，和 N 分開計。N−M 不是缺件數 |
| 完成條件 | N>0、M=N、U=0。完成不代表沒有缺件或損壞 |
| 非完成狀態 | 下列狀態各自獨立，都**不算完成**：沒有可清點組件（N=0）、完成度不完整（U>0）、不需要清點、未完成 |
| 範圍 | 在藏和借出的副本在範圍內，但借出的不能實際清點。售出、送出、遺失退出範圍；狀態未知另外列出，視為可能漏計。封膜是操作限制，不影響是否在範圍內 |
| 完成日期 | 完成時，取目前適用組件的使用者清點日期最大值 |
| 系統確認時間 | 從未完成變成完成時，判定成功的系統時間；一般儲存不等於確認 |
| 轉換 | 完成→完成：重算完成日期，確認時間不變，不寫事件。完成→未完成：隱藏目前的雙時間，寫「失去完成」。未完成→完成：寫「達成完成」，記新的確認時間。未完成→未完成：不寫事件。失敗或版本衝突時全部不變 |
| 初次 | 起點是「尚未判定」，不保存虛構的未完成歷史。第一次就符合完成時寫「達成完成」；不符合則只保存「未完成」判定，不寫「失去」 |
| 退出／重返（B） | 退出不改最後判定，也不寫事件。只有在所有排除條件都解除後才算重返，重返時重新判定；事件時間是重判當下，不倒填 |
| 歷史 C | 保存每次成功清點，以及進入／失去完成資格的轉換。唯讀；目前值與事件在同一交易寫入，不從事件重建目前值 |
| 清點事件欄位 | 副本×組件、順序、確認數量、使用者日期、系統儲存時間、前值（同一交易寫入前的數量、日期、狀態，要區分「無紀錄／有紀錄但缺值／有值」）、當時預期數量、來源類別與操作人 |
| 轉換事件欄位 | 副本、順序、轉換類型、系統事件時間、達成時的完成日期、轉換後的 N／M／U、判定理由集合、規則版本、來源類別與操作人 |
| 冪等語意 | 同一個鍵、同樣的完整內容，原本已成功：不再寫入，重播原結果。同鍵不同內容：拒絕。鍵要綁定身分、操作類別與目標。只有確知完整回滾時，才可以用同鍵同內容重試。冪等**不能**取代版本守衛 |
| 操作人 | 人工或系統兩類；人工記錄後端驗證過的身分，系統來源不虛構人名 |

### 7.1 補充盤點（Claude，2026-11-26）

- 分類器（`component-classifier.ts`）把每個組件定義分成 `PHYSICAL_COMPONENT`、`LEGACY_PRODUCT`、`UNKNOWN` 三類，並提供 `canUseForInventory`。正式環境 178 個定義，其中歷史商品 149、UNKNOWN 29、已確認實體 0（2026-11-17 快照）。
- 所以有 UNKNOWN 定義的收藏，在 C1 上線後會顯示「完成度不完整」，這是規則要求的結果（U>0 不能判完成），不是錯誤。
- R06 的副本選單只列「在藏且未封膜」的副本，所以頁首只會顯示這些副本的進度。借出、封膜副本的進度要等 R05 擴充時才看得到（Q93）。

### 7.2 判定規格（`box-v1`）

對收藏 C 的每個副本 X，逐項判斷：

1. **組件分類**：取收藏 C 的全部組件定義，用 `classifyStoredComponents` 分類。
   - `PHYSICAL_COMPONENT` 且 `canUseForInventory`：**已確認組件**。
   - `UNKNOWN`，或是 `PHYSICAL_COMPONENT` 但不能用於清點（衝突、證據不符）：**資格未確認**，計入 U。
   - `LEGACY_PRODUCT`：不是實體組件，**不計入** N 或 U。
   - 分類回報 `EVIDENCE_UNAVAILABLE`：整個判定失敗，拋出錯誤，不得回報任何狀態。
2. **N**：已確認組件中，對 X 適用（`v2_component_applicability_current` 沒有 `not_applicable = 1`）的種類數。
3. **M**：N 裡面，X 的清點列 `inspection_status = 'checked'` 而且 `actual_quantity` 不是 NULL 的種類數（0 有效）。
4. **U**：收藏 C 中資格未確認的定義數（收藏層級，每個副本相同）。
5. **理由集合**（可以同時有多個，依下列順序排列）：
   - 收藏已封存：`COLLECTION_ARCHIVED`。
   - X 的 `inventory_status` 是 `sold`、`gifted_away`、`lost`：`NOT_IN_SCOPE`。
   - N=0：`NO_APPLICABLE_COMPONENTS`。
   - U>0：`UNVERIFIED_DEFINITIONS`。
   - M<N：`UNCOUNTED_COMPONENTS`。
6. **狀態**：
   - 理由集合是空的才是 `complete`；
   - 否則依第一個理由對應：`archived`、`not_in_scope`、`no_applicable_components`、`unverified`、`incomplete`。
   - `inventory_status = 'unknown'` 的副本另外標記 `inventoryUnknown: true`（可能漏計），判定照常進行。
   - 借出、封膜都照常判定，不另加理由。
7. **完成日期**：只有 `complete` 時才計算，取 N 個組件的 `counted_on` 最大值。只要有任何一個是 NULL（舊資料），完成日期就是 `null`，畫面顯示「未記錄」；不得改用 `last_checked_at`。
8. **系統確認時間**：C1 一律是 `null`，畫面顯示「尚未記錄」（C2 才會有）。
9. **讀取**：用 `db.batch()` 或單一查詢讀取副本、清點列與適用性，**不得用複合 SELECT**（#10 的段數上限）。任何讀取失敗就拋出。
