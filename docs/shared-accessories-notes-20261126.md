## 1. 外部意見重點

- **五種配件類型**：
  - A. 單一桌遊專屬（Dedicated）；
  - B. 系列共用（Series Shared，例如詭鎮奇談的壓克力混沌 Token）；
  - C. 跨桌遊共用（Multi-game Shared，例如金屬錢幣、木製資源）；
  - D. 全域通用（Universal，例如骰塔、桌墊、桌遊桌配件）；
  - E. 庫存分配型（Inventory Allocated，例如卡套、自黏袋），和既有的卡套庫存與 USE 扣帳相近。
- **例子**：一組金屬錢幣給 5 款遊戲用。擁有 1 套、實體 100 枚、適用 5 款；成本只能計算一次；建議「獨立計入」配件類別，**不平均分攤**到各遊戲；刪除其中一款遊戲的收藏，不連帶刪除配件。
- **配件的適用關係不等於套組的包含關係**：一組混沌 Token 適用整個詭鎮奇談，可以由下層的循環繼承；但不能被誤認為擁有 10 組。
- **建議區分五種關係**：套組包含、遊戲擴充、配件適用、配件配置、採購入帳。
- **候選規則 ACC-01～ACC-13**：
  - 配件有獨立的收藏身分；
  - 可以適用多款遊戲，也可以適用大套組或小套組；
  - 允許全域配件，不綁任何遊戲；
  - 共用關係不增加實體數量；
  - 成本不重複計算；
  - 移除適用關係不刪除配件；
  - 專屬配件可以指定實體副本；
  - 套組下層繼承適用性；
  - 庫存分配和重複使用分開管理；
  - 同時使用的數量限制（預留）；
  - 成本分攤（暫不實作）；
  - 配件的實體清點（待評估）。
- 外部意見建議 #32 收藏套組與「共用配件管理」**互相關聯，但不互相依賴**。

## 5. 待使用者批准的候選修訂（依「改已採納規則須先批准」，批准前不寫進工作命令）

### 5.1 R16 修訂候選：BGG 配件也能當適用關係的來源

- **原因**：Q110-B 規定配件來源沿用 BGG 與 NotBGG。但 R16 目前只接受 NotBGG 配件當來源，所以 BGG 上有條目的配件（例如外部意見舉的 Nemesis 專用遊戲墊、克蘇魯桌墊）沒辦法記錄適用對象。
- **影響**：
  1. `site_game_relations.source_game_id` 的外鍵指向 `notbgg_games`。要讓 BGG 配件當來源，**需要 Migration**；SQLite 要改外鍵，得重建資料表。
  2. 需要一個新的寫入入口：目前只有 NotBGG 配件頁有。
  3. 公開網站的相關遊戲投影、系列花費（`series-spending.ts:48,63`）都要一起核對。
  4. 既有的 R16 資料列、白名單、封存規則不變。
- **狀態**：✅ **已採納**（2026-11-26，DECISION_LOG R16-REV-01）。只批准規則修訂；實作（Migration、寫入入口）另開工作命令。

### 5.2 Q64 修訂候選：適用關係不帶入成本（依 Q112）

- **原因**：Q112 規定成本以採購訂單及採購明細為依據，不以配件適用關係決定。但已採納的 Q64 會沿著配件關係（收藏層的 `accessory_for`，以及 R16 的 `site_game_relations`）把配件收藏的成本**併入系列合計**。一個共用配件連到 5 個系列時，會在 5 個系列的合計裡各出現一次。
- **可能的修訂方向**（請使用者選擇或補充）：
  - (a) 系列合計只計入系列內收藏自己的分攤；配件改列在「相關配件」區塊，顯示配件自己的採購成本，但**不併入**系列合計。
  - (b) 只有專屬配件（只連到這個系列）併入合計，共用配件另外列出。
- **影響**：系列花費（#29，已上線）的合計數字會改變；R01 與採購頁的全站總額不受影響。
- **狀態**：✅ **已採納方向 a**（2026-11-26，DECISION_LOG SERIES-Q64-REV-01）：配件一律另列，不併入系列合計。#29 的程式要另開工作命令修改，修改前畫面維持原樣。

## 10. Q114 適用範圍狀態（2026-11-26，DECISION_LOG ACC-Q114）

| 子題 | 決定 |
| --- | --- |
| Q114-1 記在哪一層 | 遊戲資料層（配件商品層級，BGG 或 NotBGG 條目），和 R16 適用關係同一層；不記在收藏或實體副本層級 |
| Q114-2 怎麼表示 | 「全域通用」用明確的標記，由使用者主動設定並留下紀錄。「尚未指定」不另存：沒有全域標記、也沒有有效適用關係時，自動推導。「指定適用」：有任何一筆有效適用關係時推導 |
| Q114-3 能否並存 | 互斥。設為全域時不能有有效適用關係；已有關係時要改成全域，必須先封存那些關係（保留歷史，符合 Q110-E） |
| Q114-4 提醒 | 「尚未指定」只在配件清單提供篩選，不加入 R01 待處理 |

**狀態推導表**：

| 全域標記 | 有效適用關係 | 狀態 |
| --- | --- | --- |
| 有 | 0 筆 | 全域通用 |
| 無 | 1 筆以上 | 指定適用（對象可以是遊戲；#32 之後也可以是套組） |
| 無 | 0 筆 | 尚未指定 |
| 有 | 1 筆以上 | 不允許，由寫入守衛擋下 |

**實作備註（給之後的工作命令，未授權）**：
- 全域標記與 R16 適用關係都以遊戲身分為鍵。NotBGG 配件已經有 `v2_games` 列；BGG 配件要到建立收藏時才會寫入 `v2_games`，所以 R16-REV-01 實作時，要決定在建立適用關係或設定全域時，是否先補建 `v2_games` 列。
- 互斥規則要在資料庫層守住（觸發器或條件式寫入），不能只靠畫面。

| Q115-1 意義 | 副本層級只代表**實際配置**：某一份配件實體（配件收藏的副本），現在配給哪一份遊戲副本。適用範圍仍只在商品層（Q114），兩者不混用 |
| Q115-2 數量 | 一份配件實體同時最多配置給一份遊戲副本；要換副本，先解除再配置。輪流使用的共用配件（金屬錢幣等）不做配置，只用適用關係表示 |
| Q115-3 前提 | 遊戲副本必須在配件的適用範圍內：屬於「指定適用」的對象，或配件是「全域通用」。尚未指定的配件要先設定適用對象。由資料庫守住 |

**沿用的固定規則（不需另外決策）**：
- 配置不影響成本（ACC-Q112：成本以採購為依據）。
- 配置不影響遊戲副本的實體清點（N／M／U）。配件的組件在配件自己的收藏清點，不併入遊戲。
- 新增或解除配置都不會建立或刪除配件收藏與副本（Q110-E）。
- 卡套仍走自己的套用機制（E 類），不納入這裡的配置。

**留給後續子題**：
- 解除、封存時的歷史保留 → Q117。
- 「適用範圍變更後，已配置的副本不在範圍內了」怎麼處理 → Q116／Q117 一起討論。

## 12. Q116 適用與配置的區別（2026-11-26，DECISION_LOG ACC-Q116；第二階段實作）

### 12.1 Q116-1：適用範圍變更與既有配置

**核心契約**：任何適用範圍變更，都不得使既有有效配置變成不合法（Q115-3 從「新增時檢查」升級為「持續成立」）。

- **驗證最終狀態**：不是只看被封存的那一筆，而是驗證整筆操作完成後，所有有效配置是否仍在最終的有效適用範圍內。範圍來源包括直接 R16 關係，以及 #32 之後的套組繼承。
- 不符時，**整筆拒絕**並列出受影響的配置，由使用者明確解除或轉移。不自動解除，也不保留範圍外的配置。
- 「封存全部關係並設為全域通用」在同一筆交易完成時，最終狀態合法，所以允許；這是正常的最終狀態驗證，不是特例。

| 操作情境 | 變更後的配置是否仍合法 | 結果 |
| --- | --- | --- |
| 封存沒有配置的遊戲關係 | 是 | 允許 |
| 封存唯一支持既有配置的關係 | 否 | 拒絕 |
| 封存直接關係，但仍有套組繼承 | 是 | 允許 |
| 封存套組關係，但仍有直接關係 | 是 | 允許 |
| 封存全部關係並改為全域通用 | 是 | 允許 |
| 取消全域通用，沒有其他適用關係，且存在配置 | 否 | 拒絕 |
| 全域改為指定，涵蓋全部既有配置 | 是 | 允許 |
| 全域改為指定，只涵蓋部分既有配置 | 否 | 拒絕 |
| 封存最後一筆關係，而且沒有任何配置 | 是 | 允許，狀態轉為尚未指定 |

**守衛涵蓋的操作**：
- 封存或變更 R16 關係；
- 取消全域通用、全域改為指定；
- 封存套組適用關係、將遊戲移出套組、修改套組階層（#32 與 #33 整合時要特別注意）。

新增適用關係原則上不會縮小範圍；修改採購成本、修改配件名稱都不需要這個守衛。

**交易要求**：
- 整筆原子提交；
- 提交時重新驗證，防止其他操作同時新增配置；
- 不留下部分封存或部分修改的結果；
- 封存與配置變更都保留歷史；
- 不得修改採購成本。

**待實作時核對**（外部意見標為候選，需要用 repo 確認）：套組間接影響、原子提交、並行守衛的技術做法。目前已知的事實：
- R16 已經用 `archived_at` 封存（`site-game-relations.ts`）；
- D1 `batch()` 失敗時整批回滾；
- 專案已經多次用「條件式寫入＋觸發器」處理並行（0023、0024、0026）。

### 12.2 Q116-2：遊戲副本頁的顯示

分成兩區：
- 「**已配置的配件**」：配到這一份副本的配件。
- 「**可用的配件**」：使用者擁有、而且適用這款遊戲或是全域通用的配件。

### 12.3 Q116-3：副本不在藏時

遊戲副本或配件副本不在藏（售出、送出、遺失、收藏封存）時：
- 配置**保留**，並標示「副本已不在藏，配置待解除」；
- 配件清單可以篩選這類配置；
- **不修改** R05 副本狀態的寫入流程。

這和 12.1 不衝突：12.1 管的是「適用範圍」變更，這裡管的是「在藏狀態」變更。

## 13. Q117 移除與歷史（2026-11-26，DECISION_LOG ACC-Q117）

| 子題 | 決定 |

## 15. Q119 同時使用、借用與數量限制（2026-11-26，DECISION_LOG ACC-Q119）

使用者貼上的建議，整包採納 **1A、2A、3A、4A**。Q119 的定位是「**未來擴充的保留原則**」，不是待開發的功能。

### 15.1 Q119-1：只定原則，不排程

借用對象、借用與歸還歷史、部分組件借出、預約、使用中狀態、遊玩紀錄整合，目前都不設計；**也不預留資料表或欄位**。配件適用關係與配置照原本的階段規劃。

### 15.2 Q119-2：沿用副本的「借出」狀態，且借出不等於不在藏

| 管理面向 | 借出後 |
| --- | --- |
| 收藏歸屬 | 仍然在藏 |
| 實體清點 | 暫時不能清點 |
| 實體配置 | 保留既有配置 |
| 可用配件 | 不列入 |

| 情境 | 處理 |
| --- | --- |
| 未配置的骰塔借給朋友 | 副本標記借出，不列為可用配件 |
| 遊戲連同專用收納盒一起借出 | 兩份副本各自標記借出，保留配置 |
| 已配置的收納盒單獨借出 | 保留配置，顯示「配件已借出」 |
| 遊戲借出、配件留在家 | 保留配置，顯示「遊戲已借出」 |
| 配件歸還 | 恢復副本狀態，重新判定可用性 |
| 配件售出或遺失 | 依 Q116-3 標示「配置待解除」 |

- **修正**：Claude 在 Q119-2 選項 A 的說明裡寫了「依 Q116-3，配置會保留並標示待處理」，這是錯的。Q116-3 只適用於售出、送出、遺失、收藏封存；借出不會觸發「待解除」，只顯示「已借出」。
- 借出遊戲時，**不自動**把配置的配件一起標成借出，因為系統無法確定配件是否真的一起借出。
- **尚未決定（小項）**：副本在藏狀態是「狀態未知」（`unknown`）時，配置要怎麼顯示，Q116-3 和 Q119-2 都沒有涵蓋，留待實作第二階段時一併確認。

### 15.3 Q119-3：將來的同時使用以實體數量為準

| 配件類型 | 範例 | 數量依據 |
| --- | --- | --- |
| 不可拆分 | 骰塔、桌墊、專用收納盒 | 有效的實體副本數 |
| 可拆分 | 金屬錢幣、木製資源、通用 Token | 各組件的有效實點 |

| 數量來源 | 能不能直接當作可用數量 |
| --- | --- |
| 適用遊戲數、適用套組數、採購數量、組件預期數量 | 不能 |
| 有效實點、不可拆分配件的有效實體副本數 | 可以作為依據 |
| NULL、尚未清點 | 不能假設為預期數量或 0 |
| 借出、售出、遺失的副本 | 不列入目前可用數量 |

R06 的實點是某次清點確認的結果，**不等於即時可用庫存**；將來實作時，還要考慮借出、固定配置、使用占用，以及清點結果是否仍然有效。現在不訂完整的計算公式，也不支援部分組件配置。

### 15.4 Q119-4：不綁定遊玩紀錄

| 概念 | 用途 | 規劃 |
| --- | --- | --- |
| 適用（Applicability） | 可以搭配哪些遊戲 | 第一階段 |
| 配置（Assignment） | 長期配置給哪一份遊戲副本 | 第二階段 |
| 借出（Loaned） | 實體暫時不在手邊 | 沿用 R05 |
| 使用中（In Use） | 現在哪一場遊戲正在用 | 未來另議 |

金屬錢幣這類平時獨立存放、遊玩時才取出的配件，不要求每次遊玩都建立配置、結束後再解除，避免把長期配置歷史和短期使用紀錄混在一起。

### 15.5 待核對（使用者註明）

R05 的借出狀態轉換、副本備註欄位與相關守衛都還沒有用 repo 核對；不能保證所有借出情境都不需要調整程式。
