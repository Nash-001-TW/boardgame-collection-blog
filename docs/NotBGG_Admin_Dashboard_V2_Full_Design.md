## 1. 命名與範圍

正式名稱為 **《NotBGG Admin Dashboard V2 — 收藏管理模組完整整合設計》**。過往對話中的「收藏管理 V3」僅為規劃期間的暫稱，**不代表網站版本升級、建立 V3 資料表或更名既有 `v2_*` 資料表**。

本次設計整合 BGG 與 NotBGG 的遊戲搜尋、收藏管理、實體副本、採購及 BGG 匯入同步；**不建立兩套平行的收藏系統**。

### 全域不變條件

- 同一遊戲可以有多筆收藏；同一收藏可以有 **0 至多個**實體副本。
- 新增收藏**不自動建立實體副本**。
- `game_id`、`collection_id`、`copy_id`、`purchase_id` 是不同身份，不可混用。
- BGG 與 NotBGG 來源身份應保留；NotBGG 連結 BGG 不等於合併身份。
- 保留既有 ID、Revision、封存狀態、採購、卡套、組件及其他關聯。
- 不自動重建、合併、轉換或清理既有收藏。
- 過往曾盤點 **256 筆收藏**，此為歷史基準，**不是已驗證的當前正式筆數**。

## 4. M1 收藏列表規格

- **預設依 `game_id` 分組**，可切換逐筆 `collection_id` 模式；分組僅影響顯示，不合併資料。
- 支援名稱／別名、BGG ID、NotBGG ID、收藏 ID 搜尋。
- 篩選來源、收藏意願、封存狀態、副本數、語言、保存狀況及異常狀態（依實際資料能力）。
- 群組列可顯示封面、名稱、來源、收藏數、副本數、狀態及更新時間；展開後顯示每筆收藏。
- 伺服器端分頁建議 25／50／100，分組與分頁順序必須正確，排序穩定。
- 收藏封存與還原需明確確認；不得連帶刪除副本、採購、卡套與組件。
- 列表搜尋僅查站內資料，不在每次列表查詢時呼叫 BGG 線上 API。

## 5. M2 標準新增收藏規格

四步驟：**搜尋選擇遊戲 → 檢查既有收藏並分流 → 填寫收藏基本資料（副本／採購選填） → 預覽確認與儲存**。

- 遊戲尚未收藏：建立新收藏，可不建立副本。
- 已有收藏但增加另一盒：優先引導新增副本。
- 確實需要同遊戲的獨立收藏：顯示提醒後允許新增另一筆收藏。
- 卡套及組件可留到收藏詳情頁管理。
- 新增操作應有身份檢查、冪等性及跨表一致性防護。
- BGG 遊戲主資料匯入與收藏建立是獨立操作；取消收藏建立不能留下未確認的收藏／副本／採購。

## 6. M3 統一搜尋規格

- **站內優先**，由使用者明確按下「搜尋 BGG 線上資料」才呼叫外部來源。
- 支援名稱、別名、BGG ID、NotBGG ID；結果標示來源、類型（主遊戲／擴充）、站內身份、連結狀態、收藏數及副本數。
- 區分站內 BGG、站內 NotBGG、已連結 BGG 的 NotBGG、尚未匯入的 BGG 線上結果。
- 搜尋與預覽唯讀；匯入前必須確認身份與資料差異。
- 同名不等於同一遊戲；BGG 連結不等於 NotBGG 身份合併。
- 重複 BGG ID 應重用既有主身份，不建立重複遊戲。

## 7. M4 分頁式收藏編輯規格

六個分頁：

1. **基本資料**：收藏狀態、意願、個人評分等。
2. **實體副本**：每盒語言、版本、保存狀況等。
3. **採購紀錄**：交易、金額、日期、通路與關聯。
4. **卡套與組件**：尺寸、數量、配件及所屬關聯。
5. **評論與備註**：個人評論、遊玩紀錄、備註。
6. **修訂紀錄**：可取得的版本與修改摘要；若現有系統不具備完整歷史，須標示限制。

**各分頁獨立儲存**；副本／採購的新增與編輯進一步採單筆操作。未儲存切換需提醒，失敗需保留輸入。

### 安全儲存

- 現有 PATCH 可能是**完整表單替換**，P0 必須核對。不得直接將分頁局部資料送至可能清空未提供欄位的 API。
- 未來目標是明確的欄位級更新契約，區分未提供、`null`、空字串、`0`、`false`。
- Revision 必須由後端**原子驗證**，過期提交應拒絕並保留本地草稿供比較。
- 編輯收藏不可直接更換 `game_id`；身份轉換是獨立流程。
- BGG 主資料不在一般收藏編輯中直接修改。

## 8. M5 實體副本與採購規格

### 副本

- 一筆收藏可有 0～多個副本；建議每個 `copy_id` 代表一個可獨立管理的實體單位。
- 目標欄位：副本名稱、語言、出版版本、保存狀況、取得日期、存放位置、備註及修訂資訊。
- 既有資料若使用數量式記錄，不得自動拆分。
- 卡套、組件究竟屬於收藏或副本，須先核對現有 Schema；不因編輯副本而移除原關聯。
- 封存副本為建議能力，須先確認既有 Schema 是否支援，不得以永久刪除冒充封存。

### 採購與副本多對多（已確認業務目標）

- 一筆採購可關聯多盒；一盒可關聯多筆採購／付款紀錄。
- 目標欄位：採購日期、付款日期、收貨日期、金額、幣別、通路、訂單編號、運費、折扣、補款、退款及備註。
- **已確認（更新）**：單筆採購若包含多套桌遊，商品成本須由使用者手動分攤至各個「採購計價單位」；每個計價單位可是一盒桌遊，也可是一整套含主遊戲、擴充、配件及 PROMO 的套組。計價單位內不強制再次分攤。單套 ALL-IN 採購可直接整組計價。訂單金額、現金流、計價單位成本與副本成本必須區分，避免重複計算。
- 先檢查 `v2_collection_management` 與現有採購表是否已能表達多對多；只有必要時才**提出**新增關聯表／Migration 方案。
- 移除某個副本的採購關聯不得刪除仍被其他副本使用的採購紀錄。

#### 採購計價單位、套組內容與附加費用（已確認）

**三個層級不可混淆：** `Purchase`（整筆採購訂單）→ `Purchase Cost Unit`（採購計價單位）→ 套組內容（獨立收藏／實體副本／配件／PROMO）。此為**邏輯模型**，不是已核准的 D1 表名或 Migration。

1. **單筆購買一套 ALL-IN**：整套為一個計價單位；主遊戲與各擴充仍各自出現在收藏清單，保有各自 `collection_id`，但價格只記錄在套組計價單位，不強制分配到主遊戲、擴充、配件或 PROMO。個別成本應顯示「未指定」，**不可視為 NT$0**。
2. **單筆購買三套桌遊**：一筆採購可有三個計價單位，商品購買成本須分攤至這三個單位。每套本身可能包含多盒、擴充、配件或 PROMO；成本**在該計價單位止步**，不強制再往內分攤。計價單位**不等於**實體盒數或 `collection_id`。
3. **內容關聯與成本分攤分離**：一個計價單位可關聯多筆獨立收藏，亦可記錄不必建立收藏的配件／PROMO。建立或移除內容關聯不得自動變更訂單交易或套組價格。若沒有實體副本，仍須評估能否直接關聯收藏；實際 Schema 待 P0。
4. **附加費用不分攤**：運費、刷卡／交易手續費與其他採購附加費用記錄於採購層，**不得納入計價單位商品單價，也不得作為商品未分攤差額**。費用應保留類別、金額、幣別及應付／實付語意；不可因新增費用而默默調整任何計價單位成本。
5. **分攤狀態**：區分「整組計價（已完整記錄）」、「商品待分攤」、「商品部分分攤」、「商品已完成分攤」。整組計價不是未完成；允許長期保留有意不分攤的套組內成本或明確標記的未分攤餘額。
6. **退款**：退款交易保留在採購層，可選擇標記相關計價單位／副本及售後事件，但**關聯本身不自動扣減其成本**；若需變更計價單位成本，須另經人工確認調整，並避免重複扣除。運費退款亦不自動改變桌遊商品單價。

**示範案例（非正式資料）**：採購 P001 包含套組 A（主遊戲＋擴充＋PROMO）NT$3,200、套組 B（主遊戲＋兩擴充）NT$4,000、桌遊 C NT$1,800；三個計價單位的商品成本合計 **NT$9,000**。另有運費 **NT$250** 與手續費 **NT$50**，全部已付款且無退款時，實際總支出為 **NT$9,300**。商品分攤狀態為「已完成」，運費與手續費 **NT$300** 留在採購層，不屬於未分攤商品成本；各套內部擴充／PROMO 的個別成本仍為「未指定」。

**計算與報表口徑**：

- 商品成本合計＝計價單位商品成本合計；商品未分攤差額＝**商品可分攤基準額 − 計價單位已分攤商品成本**，不得把運費／手續費放入此差額。
- 採購原始應付額需區分商品、附加費用與適用折扣；已付款是實際入帳的付款交易合計；已入帳退款是實際收到的退款合計；**採購實際淨支出＝實際已付款 − 已入帳退款**。未支付尾款與未入帳退款不得提前納入實際現金流。
- 報表至少分列：商品成本、採購層附加費用、原始應付額、已付款、已入帳退款、實際淨支出、計價單位已分攤商品成本、商品未分攤差額及其原因、整組計價／分攤狀態。**採購淨支出與計價單位分攤成本是不同指標，不能直接相加**。
- 訂單折扣的商品分攤基準、退款沖正、各幣別精度與四捨五入尚待後續細化；未確認前不得自行推定或修改歷史金額。歷史只有混合總額時，不得假設全額皆為商品成本或自動拆出運費。

#### 業務案例：套組缺件折扣退款

- 原始預購套組付款 **NT$3,200**，套組部分配件短缺，代理商以 **NT$200** 折扣退款補償。
- 採購主紀錄仍保留原始付款 NT$3,200；新增**售後事件**（缺件原因、受影響配件／數量、代理商、反映日期、處理經過及結果）；另新增**退款交易** NT$200（日期、方式、入帳狀態），以關聯識別售後事件。
- 退款實際入帳後，**採購實際淨支出為 NT$3,000**。若 NT$200 未指定副本，個別副本原已分攤成本**不變**，採購層另列「未分攤退款 NT$200」，不得隱藏差額或重複扣減。
- 缺件問題即使因退款而結案，實體組件的「仍短缺」狀態不可自動改為「已補齊」。

#### 邏輯資料模型（不是已確認的 D1 實體表）

1. **Purchase（採購主紀錄）**：訂單身份、通路、訂購日期、原始商品／運費／折扣、應付額與幣別。
2. **Financial Transaction（財務交易）**：付款、退款、補款及費用調整；保留原幣、金額、交易日期、匯率或實際帳單台幣金額、換算來源及入帳狀態。費用調整與實際付款不可重複計入成本。
3. **Purchase Cost Unit／內容關聯／成本分攤（邏輯層）**：採購可有多個計價單位；各單位可關聯多個 `collection_id`、`copy_id` 或非收藏配件／PROMO；商品成本在計價單位層人工分攤。既有 Purchase–Copy 多對多能力須保留或相容；內容關聯不等於成本分攤，移除關聯不刪除共享採購。
4. **After-Sales Case（售後事件）**：穩定事件 ID、`purchase_id`、問題類型（缺件／損壞／錯品等）、原因與描述、受影響副本／組件（選填，可有多個）、預期與實際數量、代理商／通路、反映及結案日期、處理方式、狀態、備註、Revision／稽核。
5. **Case–Transaction Link（售後／交易關聯）**：售後事件可無退款（例如補寄）、可對應多筆退款；**一筆退款交易最多關聯一個售後事件**，亦可不關聯；不得重複計入退款金額。實際 Schema 待 P0 核對。

**操作歸屬與衝突保護**：採購分頁負責財務交易、售後事件及副本成本分攤；副本／組件分頁負責實體缺件狀態。更新跨關聯資料時，後端應驗證相應 Purchase、Transaction、Case、Allocation／Copy 的版本或等效衝突保護；必要的多筆異動應原子提交，避免孤兒關聯、部分更新與雙重扣款。具體 Revision 方案待 P0 驗證。

**數值語意**：分別呈現原始應付額、已付款、已入帳退款、實際淨支出、已分攤副本成本、未分攤退款。未收到的退款不得提前扣減已實現現金流；尚未支付的尾款不得算成已付。多幣別付款各自保存實際歷史換算，不用單一訂單匯率覆蓋多次付款。已確認**未分攤餘額可長期保留並標記**；精度、四捨五入與沖正細節屬後續細化事項。

**P0 優先核對**：既有採購、組件缺件、備註、交易、關聯、Revision 與稽核能力；既有單一購買金額的實際語意；能否區分商品／運費／手續費／折扣／退款、能否關聯多筆收藏及多個計價單位、無副本時能否記錄套組內容、歷史混合總額的資料風險；是否需要新增售後事件／交易／關聯結構。不得假定現有 D1 已存在上述表或欄位；不得自動將舊金額拆分為虛構交易，也不得未經授權建立 Migration。

**M5 驗收案例**：一單多盒／多套、套組內容各自收藏但整組計價、商品分攤止於計價單位、運費／手續費留在採購層、套組多配件缺件、整單退款不指定副本、同一事件分次退款、一筆退款最多關聯一事件、無退款而補寄、退款已入帳但缺件未補齊、事後手動調整、交易／事件封存、並行修改衝突、跨採購關聯拒絕與避免重複計算。

## 9. M6 BGG 匯入與同步規格

### 匯入

流程：**站內搜尋 → 手動 BGG 線上搜尋 → 身份檢查 → 詳細資料解析 → 預覽 → 明確確認匯入**。

### 同步

- 已確認 **單款手動 + 批次手動**；**不自動排程**。
- 同步前預覽差異，僅更新允許的 BGG 來源欄位。
- 可同步來源：名稱、描述、年份、玩家數、時間、設計師、出版社、分類、作品關聯、封面、BGG 評分／排名／複雜度等，依實際欄位映射確認。
- 不可同步覆寫：個人評分、評論、遊玩次數、收藏狀態、實體副本、採購、卡套、組件及 NotBGG 自建身份。
- BGG 原始值與使用者自訂覆寫值應分層；未確認現有結構前採保守同步。
- API 欄位缺失、解析失敗或不完整回應不得直接清空既有值或關聯。
- 批次每款遊戲獨立驗證與提交，記錄成功／失敗／略過；支援受控重試與限流。
- 來源身份不一致、Revision 衝突或無法安全判定時停止並要求人工確認。

## 12. P0 純唯讀盤點範圍

P0 應檢查六大面向：

1. **Schema**：實際表、欄位、外鍵、索引、約束、多對多能力及 Migration 對照。
2. **API 安全**：Route、Request／Response、PATCH 語意、Revision、Idempotency、交易與權限。
3. **副本／配件**：語言、版本、保存狀況、卡套與組件歸屬及數量語意。
4. **採購與售後**：商品／附加費用／折扣語意、採購計價單位及套組內容、單筆採購關聯多筆收藏／副本、手動分攤、獨立付款／補款／退款、幣別及副本映射；缺件／售後事件、組件數量、退款交易關聯、未分攤退款與稽核能力。
5. **BGG**：搜尋、匯入、同步、快取、Parser、來源欄位與自訂覆寫保護。
6. **資料安全**：正式資料基準、備份／回復策略、測試與回歸能力。

### P0 執行界線

- **只讀取 Repository、Migration、既有測試及現有快照**；不得修改檔案。
- **P0-01 已確認：預設不連線正式 D1**。Codex 必須先提出逐條唯讀 SQL 清單、目的、涉及資料表／欄位、預期輸出與風險；**使用者逐項審核核准後**才可執行核准的查詢。即使只有 `SELECT`／`COUNT`／`GROUP BY`，未核准仍不得執行；核准不可擴大至其他查詢。
- 不執行 Migration、測試寫入、外部 API 同步、部署或資料修復。
- 每項結論附檔案路徑／行號證據，標示 `Confirmed`、`Inferred` 或 `Unknown`。
- P0 完成只交付報告，不自動開始 P1。

### P0 交付報告

Executive Summary；Repository 架構；Database Schema Inventory；API Inventory；六大模組能力矩陣；Data Ownership Matrix；Migration 必要性評估；Risk Register；資料保護／回復方案；Test Gap Analysis；P1～P8 建議；待決策事項。

每階段須依序：**唯讀盤點 → 提案 → 使用者核准 → 實作 → 測試 → 驗收 → 另行核准部署**。


### P5a 新增驗收案例（2026-11-09 採購附加費用決策）

| ID | 驗收情境 | 預期結果 |
|---|---|---|
| P5a-01 | 一筆採購包含三套桌遊 | 三個計價單位；各有明確商品成本 |
| P5a-02 | 三套商品分攤 NT$3,200＋NT$4,000＋NT$1,800 | 商品分攤合計 NT$9,000，狀態「已完成」 |
| P5a-03 | 套組 A 含主遊戲、擴充與 PROMO | 各收藏獨立顯示；套內不強制再分攤；未指定不等於零元 |
| P5a-04 | 訂單增加運費 NT$250 | 商品單價與商品分攤狀態不變；運費留在採購層 |
| P5a-05 | 訂單增加手續費 NT$50 | 採購應付額增加 NT$50；各計價單位商品成本不變 |
| P5a-06 | 三套商品 NT$9,000，附加費用 NT$300，全部付款 | 淨支出 NT$9,300；商品分攤已完成；不誤報 NT$300 未分攤 |
| P5a-07 | 訂單僅部分付款 | 應付額與已付款分開顯示，未付額不列入實際已付款 |

| P5a-10 | 修改附加費用或套組內容關聯 | 不靜默修改商品分攤／原始交易；後端 Revision 衝突受保護 |
| P5a-11 | 舊採購只有一個混合總額 | 不自動假定全為商品或拆分附加費用；保留原始值並標示待確認 |
| P5a-12 | 同一套組內多筆收藏／多個副本 | 列表獨立、採購關聯正確，總成本只計一次 |

**階段界線**：P5a／P5b 是建議拆分的實作階段，須待 P0 驗證現有 Schema、API 與回復方案後，再逐階段取得實作及部署授權。

## 15. 資料保護與驗收基準

- 歷史 256 筆收藏不可當作當前正式數量；部署前需另行授權取得最新唯讀基準。
- 驗證收藏／遊戲／副本／採購 ID 集合與所有關聯，並核對卡套、組件、封存及 Revision。
- 備份／回復須區分 **Workers 程式版本回復、D1 Schema 回復、D1 資料內容回復**。
- 未取得授權前不得進行備份、還原、正式資料查詢、Migration 或部署。
- 不得以「測試通過」取代正式部署核准。

## 16. 明確排除範圍

- NotBGG 與 BGG 自動身份轉換或收藏合併。
- 大規模重建／清理既有收藏。
- BGG 自動排程同步。
- 未經確認的舊副本拆分、採購分攤或資料推定。
- 無條件強制覆寫 Revision 衝突。
