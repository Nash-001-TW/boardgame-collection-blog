# D1-S1／S2｜勘誤狀態、交易與儲存候選設計

2026-11-19（台北）。狀態為設計中，待 Claude 獨立審查。已批准的第一版方案 A 與證據保存方案 A 見 [範圍與業務驗收](V2-D1-expected-quantity-correction-scope.md)。本稿提出邏輯紀錄與約束，尚未選定 Schema、API、交易實作或 Migration。

## 1. 狀態與合法轉換

建議以「公告版本 × 目標共用組件定義」識別一個審查目標。三種狀態對外沿用；其中 `APPLIED` 從已提交的更正紀錄推導。這讓更正紀錄與狀態只有一個事實來源。

| 目前狀態 | 動作與條件 | 結果 |
| --- | --- | --- |
| 尚未登記 | 保存公告版本和目標 | `PENDING`，預期量維持原值。 |
| `PENDING` | 仍欠證據或已核對整體範圍但尚未提交 | 維持 `PENDING`，追加審查理由。 |
| `PENDING` | 確認完全不適用，或只涵蓋部分版本 | `NOT_APPLICABLE`，記錄具體理由，公告可回查。 |
| `NOT_APPLICABLE` | 有新證據或目標適用範圍改變，管理員重新開啟審查 | `PENDING`，留下重開原因與歷史。先前理由仍可回查。 |
| `PENDING` | 全範圍已確認，且更正交易成功提交 | `APPLIED`，關聯實際更正紀錄。 |
| `APPLIED` | 舊請求重播，或後續收到新版勘誤 | 原目標維持 `APPLIED` 並可重播原結果。新版勘誤建立新公告版本及新審查目標，成功後才追加下一次更正。 |

`APPLIED` 表示該公告曾成功套用。後續勘誤再次改變目前預期量時，舊公告仍顯示已套用，歷史顯示當時更正後的值。目前值從共用定義讀取。同一公告的其他目標各自判定。第一版以單目標為提交單位；若管理員依序處理多個目標，介面須分別回報結果。

## 2. 儲存模型候選

| 邏輯紀錄 | 起碼需保存 | 候選約束 |
| --- | --- | --- |
| 公告版本 | 來源、網址或附件參照、發布時間（可未知）、取得時間、原始說法、勘誤內容、版本條件；有新版時可追到前一份 | 已用於審查或套用的證據版本可追溯。來源更新時追加版本，保留既有依據。網址可以重用，單靠網址不足以辨識公告版本。 |
| 審查目標與審查歷史 | 公告版本、共用定義、判斷範圍及理由、審查人與時間、可驗證的目前審查依據 | 同一公告版本 × 共用定義只有一個目標。狀態變更及重開理由追加保存。未有更正時從目前審查結果判定 `PENDING`／`NOT_APPLICABLE`。 |
| 成功更正與可重播結果 | 目標、舊值／新值、確認的範圍、依據版本、操作者與成功時間、請求識別及不可混用的內容綁定、可可靠回傳的原結果 | 同一目標最多一筆成功更正。唯一的操作識別可核對同次提交；有對應更正才顯示 `APPLIED`。後續勘誤另建目標。 |
| 尚無成功結果的請求識別 | 若最終選型需要單獨保存，須能辨識原請求內容與過期狀態 | 即使已知回滾，同一識別也不可換內容重送。識別簽發、持久方式、期限與清理待選。 |

能重建 `103／99 → 少 4` 的歷史至少需要當時採用的預期量與該次有效實點，或可定位這兩筆歷史的引用。只保存舊／新預期量，再讀後來可能改變的目前實點，無法還原原判讀。候選是保留不可變的歷史引用；如果既有資料無法可靠重建，才評估為受影響副本保存最小快照。暫未選定儲存形式。

## 3. 交易一致性與請求重送

1. **先識別原請求。** 已提交且內容一致，回原成功結果；同識別但內容不同，拒絕。即使目標後來被新公告更正，原請求仍回自己的原結果。
2. **在提交邊界重新確認。** 核對管理員權限、公告版本與目標、審查結論是否仍涵蓋整個共用範圍，以及預期舊值與相關依據仍有效。舊值相同但範圍或公告版本已變，也應拒絕過期確認。確認方法與版本機制待實作規劃。
3. **一致提交。** 同一交易更新共用預期量並保存成功更正與可重播結果。若後續選擇額外保存 `APPLIED` 投影，該投影也須同一交易完成。更正不寫逐盒實點、原清點日期、checked 或清點事件，也不觸發適用性完成轉換。
4. **區分已提交、已知未提交及結果未知。** 已知回滾保留原值、原狀態與歷史。結果未知時依原識別查詢或重送同一內容；未見成功紀錄可能仍在途，不能直接判成已回滾，也不能換新識別再套用。兩人用不同識別同時套用同一目標時，目標唯一性與交易守衛應阻止第二筆成功。

**現有入口需納入審查。** [目前 R06 的一般編輯](../src/lib/physical-component-management.ts#L135) 會直接寫共用 `expected_quantity` 並遞增 `physical_revision`。未來實作前需盤點所有可改值的入口，決定如何攔住過期確認，以及勘誤更正如何留下同一份可追溯歷史。既有 revision 可列入候選，仍需確認哪些範圍與證據變化由它覆蓋。

## 4. 複審驗收案例

| 案例 | 驗收條件 |
| --- | --- |
| D1-10 成功一致性 | 103 → 100、實點仍為 99，目標顯示 `APPLIED` 且恰有一筆更正紀錄；未影響其他組件及各盒清點事實。 |
| D1-11 中途失敗 | 模擬更新共用值與保存更正結果之間的失敗；不得出現新值無歷史、舊值卻標為 `APPLIED`，或額外清點事件。 |
| D1-12 回應遺失及重送 | 成功後遺失回應，重送相同識別與內容只回原結果；改內容拒絕。若尚在途則仍回報結果未知。 |
| D1-13 併發與過期確認 | 不同識別競爭同一個目標最多一筆成功。審查範圍改變但預期舊值相同時也要拒絕過期確認。 |
| D1-14 多組件部分成功 | 同公告的 A 成功、B 因只涵蓋部分版本維持原值、C 在提交時失敗。三個目標的狀態與歷史各自補全。 |
| D1-15 重開及再次更正 | 先前部分涵蓋的目標重開時保留原判斷理由。已套用公告收到新版勘誤時，舊 `APPLIED` 和舊判讀仍可回溯。 |
| D1-16 歷史不漂移 | 勘誤後重新清點，舊畫面或查詢仍能還原原實點 99 與當時兩種判讀，不把後來的實點套到歷史。 |
